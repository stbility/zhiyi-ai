# 智一 AI™ 品牌 Agent 长期训练方案

目标:让「智一 AI」有一个**属于自己品牌、会随使用越用越准**的 Agent,而不是换个提示词的通用聊天模型。

---

## 一、先说结论:不要从「训练模型」开始

「训练自己的模型」听起来是终点,但按**每一分投入换来的效果**排,顺序恰好是反的:

| 手段 | 见效速度 | 成本 | 换服务商还能用吗 |
|---|---|---|---|
| ① 品牌人格层(系统提示 + 风格约束) | 当天 | 几乎为零 | 能 |
| ② 技能文件(可复用的工作流指令) | 一周 | 低 | 能 |
| ③ 长期记忆 + 检索(RAG) | 两周 | 低(存储费) | 能 |
| ④ 工具与集成(Git、插件) | 按需 | 中 | 能 |
| ⑤ 评测集(回归防线) | 两周 | 低 | 能 |
| ⑥ 微调 / LoRA | 一个月起 | 高(算力 + 标注) | **不能,绑死一家** |

**①~⑤ 能解决绝大多数「不像我们家的 Agent」的问题,而且全部与服务商无关。**
⑥ 只有在前五步都做完、并且评测集能证明「剩下的差距靠提示词补不上」时才值得做——否则就是花钱买一个换不了服务商的包袱,和你定的「不要写死在代码里,让系统自动链接」直接冲突。

所以方案分两条线:**主线(①~⑤)现在就做,支线(⑥)等数据攒够再评估。**

---

## 二、主线:让 Agent 变成「你家的」

### ① 品牌人格层 —— 一份可版本化的身份定义

现在 `src/lib/ai/tools.ts` 里的 `AGENT_SYSTEM_PROMPT` 是**写死在代码里的一段字符串**,改一次要发一次版,也无法按组织区分。

改成一张表:

```
brand_profiles
  organization_id   谁的品牌
  name              品牌名
  persona           身份与语气(「你是智一 AI 的工作流助手,……」)
  writing_rules     文风硬约束(用词、句式、禁用表达、标点)
  refusal_rules     什么不做、怎么拒绝
  output_contract   产出格式约定(代码进工作区、来源必须标注 …)
  version           每次改动 +1,历史保留
```

运行时:`品牌人格 + 技能文件 + 工具说明` 三段拼成系统提示。
**关键是版本化**——改了人格之后要能用 ⑤ 的评测集验证「有没有改坏」,没有版本号就无法对比。

**产出**:一张表 + 设置页里的「品牌人格」编辑器 + 拼装函数。工作量约 2~3 天。

### ② 技能文件 —— 把重复的工作流固化下来

一个「品牌 Agent」的真正差异不在语气,而在**它知道你们家的活该怎么干**。

```
skills
  organization_id
  slug              week-report / code-review / competitor-scan
  title             人看的名字
  trigger_hint      什么时候该用它(给模型判断)
  instructions      具体步骤(Markdown)
  tools_allowed     这个技能允许调用哪些工具
  enabled
```

运行时按 `trigger_hint` 让模型自己挑,或用户在输入框显式选。技能文件就是**可以被非工程师编辑的工作流**——这是「个人 AI 工作流操作系统」和「聊天助手」的分界线。

**已有基础**:`src/lib/ai/agent.ts` 的循环、`tools.ts` 的工具注册都在跑,技能文件只是给它们加一层可配置的指令来源。

**产出**:一张表 + 技能管理页 + 注入逻辑。工作量约 4~5 天。

### ③ 长期记忆 —— 越用越懂你

分三层,不要混在一起:

| 层 | 存什么 | 生命周期 | 写入方式 |
|---|---|---|---|
| 会话记忆 | 本轮对话 | 一次对话 | 已实现(`messages` + 上下文预算) |
| 项目记忆 | 某个工作区的约定、决策 | 长期 | Agent 主动写 |
| 品牌记忆 | 术语表、客户名、内部缩写、历史结论 | 永久 | 用户确认后写 |

```
memories
  organization_id
  scope             project | brand
  workspace_id      scope=project 时才有
  content           一条事实
  embedding         向量(pgvector)
  source_message_id 出处,可追溯
  confirmed_by      谁确认的,未确认的不参与检索
  created_at
```

**必须有 `confirmed_by`**:让模型自动往长期记忆里写,几轮之后就会积累一堆它自己臆想的「事实」,而且越错越自信。**记忆必须由人确认才生效**——这是和你定的「禁止假数据」同一条原则。

检索用 Supabase 的 `pgvector`,不引入第三方向量库(少一个要付费、要维护、可能在国内不通的外部依赖)。

**产出**:pgvector 扩展 + 一张表 + 检索注入 + 记忆确认界面。工作量约 5~7 天。

### ④ 工具与集成 —— 能力边界

已在路线图里(Git 集成、Hermes Agent、多品牌插件)。对品牌 Agent 的意义是:**同样的技能文件,接上不同工具就能干不同的活**。技能文件里的 `tools_allowed` 就是这层的接口。

### ⑤ 评测集 —— 没有它,后面每一步都是盲改

这是整个方案里**最容易被跳过、但一旦跳过前面全白做**的一步。

```
evals
  organization_id
  slug
  input             一段真实提问(从历史对话里挑)
  expectations      判定标准(必须包含 / 必须不包含 / 必须写文件 / 必须标来源)
  tags
eval_runs
  eval_id, brand_version, skill_version, model_id
  passed, actual_output, latency_ms, created_at
```

判定分两种:

- **硬判定**(能自动跑):有没有写文件、有没有标来源、有没有出现禁用词、JSON 能不能解析
- **软判定**(用另一个模型当裁判):语气对不对、结论有没有跑题

先做硬判定就够用了。20~30 条真实用例,每次改人格或技能就跑一遍——**这是唯一能回答「我这次改动到底是变好了还是变坏了」的东西**。

**产出**:两张表 + 一个跑评测的 Server Action + 结果对比页。工作量约 4~5 天。

## 三、数据飞轮:训练数据从哪来

你已经在积累了,只是还没有被当成资产:

```
messages          真实提问与回答,带 latency、token、错误
workspace_files   Agent 真实产出的文件
conversation_attachments  用户提供的上下文
```

要把它变成训练/评测数据,缺的是**一次人工判定**:

```
feedback
  message_id
  verdict      good | bad | edited
  edited_text  用户改成了什么(这是最值钱的数据)
  reason
```

界面上就是回答旁边加「👍 / 👎 / 我改成了这样」。
**`edited_text` 是含金量最高的一列**——它直接给出「模型写的」和「你要的」之间的差,既能做评测用例,也是将来微调的成对样本。

这一步很小(半天),但**越早开始积累越好**,因为数据只能靠时间攒。

## 四、支线:什么时候才真的该微调

同时满足这三条,再考虑:

1. 评测集里有**持续失败且改提示词无效**的一类问题(通常是极强的文风一致性、或高度专有的格式)
2. 已积累 **≥ 1000 条**人工确认过的成对样本(`edited_text` 是主力)
3. 愿意接受**绑定一家服务商**的代价

到那一步的技术选择(按代价从低到高):

| 方式 | 说明 | 代价 |
|---|---|---|
| 服务商托管微调 | DeepSeek / 阿里百炼 / 火山方舟都提供,上传 JSONL 即可 | 低,但换家要重来 |
| LoRA 适配器 | 训练一个小适配器挂在开源底座上(Qwen / GLM / Llama) | 中,适配器可迁移到同底座 |
| 自建推理 | vLLM 自托管 + LoRA | 高,要 GPU 与运维 |

**注意**:即使做了微调,①~⑤ 全部仍然有效且必须保留。微调解决的是「口吻和格式」,解决不了「不知道你们家的事实」——那永远是记忆和检索的活。

而且系统必须保持**微调模型只是模型列表里多出来的一个选项**,不能因为它而改变调用链——`ai_providers` / `ai_models` 那套已经是这个形状,自建的 vLLM 地址也能直接填进去(预设里已经有 vLLM(自建))。

## 五、建议执行顺序

和你已定的路线图合并后:

| 顺序 | 内容 | 归属 |
|---|---|---|
| 1 | **反馈按钮**(👍/👎/我改成了这样) | 数据飞轮,越早越好,半天 |
| 2 | Git 仓库集成 + Hermes Agent + 多品牌插件 | 你已定的下一步 |
| 3 | **技能文件管理**(②) | 你路线图里的「技能文件管理」 |
| 4 | **品牌人格层**(①) | 新增,2~3 天 |
| 5 | **评测集**(⑤) | 新增,做完 ③④ 必须补上 |
| 6 | 用量/成本、密钥轮换、审计日志、`supports_tools` | 你已定 |
| 7 | **长期记忆 + pgvector**(③) | 路线图里的 RAG/记忆 |
| 8 | 后台执行 + 工作流状态机 | 你已定 |
| 9 | 微调评估(⑥) | 数据够了再说 |

第 1 步是唯一一个**「现在不做,以后补不回来」**的——历史对话可以回捞,但用户当时想怎么改,过后没人记得。

---

## 六、成本

主线①~⑤:**几乎不增加经常性开销**。多的只是几张表和一点向量存储,Supabase 免费额度内。真正的成本是开发时间,合计约 3~4 周。

支线⑥:托管微调按训练 token 计费,一次几十到几百元人民币量级;自建推理要长期 GPU,月成本另一个量级。**在评测集证明必要之前不要花这笔钱。**
